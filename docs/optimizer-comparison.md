# Phase C 最適化手法の比較（HC・SA・GA・現行）

プラグボード未知版（`decrypt_plugboard.py`）の Phase C（プラグボード復元）について、
遺伝的アルゴリズム（GA）を実装し、山登り法（HC）・焼きなまし法（SA）・現行の
既定手法と同じ条件で比べた記録。数値はすべて `tools/benchmark_optimizers.py` の実測値。

## 結論

**GA の採用は提案しない。** 同じ評価回数のもとで、GA は現行（段階スコア HC＋SA 磨き上げ）を
どの計測でも上回らなかった。正解のローター・位置を与えて最適化手法だけを比べると
（oracle、各 50 試行）、完全復元はセット A で 17 対 21、セット B で 12 対 18、
適応度/字は現行より 0.22（A）・0.18（B）低かった。

GA 以外も含めて、**現行より精度が高いと言える手法は無かった**ので、既定（`--optimizer staged`）は
変えていない。唯一 SA 単独がセット A で現行を上回ったが、シードを 15 に増やした追加検証では
セット B と調整用セットで同等かわずかに下回り、一貫しなかった（後述）。
今回の条件で解読率を制限しているのは Phase C ではなく、Phase A（候補の取りこぼし）だった。

## 比べた手法

4 手法とも Rust コア（`enigma_decoder/src/core.rs`）の同じ層で動かし、Rayon で候補ごとに並列化する。
Python と Rust の速度差が結果に入らないよう、比較用の手法も含めてすべて Rust に置いた。

| 名前 | 中身 | 実装 |
|---|---|---|
| current（現行） | 段階スコア HC（IC→bigram→trigram）を空の plugboard と `n_restarts` 個のランダム初期値から実行し、最良解を SA（40,000 ステップ、温度 12→0.3）で磨く。`decrypt_plugboard.py` の既定 | `current_search`（既存の `phase2_staged_one` と同一の結果） |
| hc | 段階スコア HC だけを、予算が尽きるまでランダム初期値から再スタート | `hc_until_budget` |
| sa | SA（40,000 ステップ、trigram+quadgram）＋貪欲 HC 磨きを、予算が尽きるまで空の plugboard から再スタート（既存の Tier-2 SA `phase2_sa` と同じ形） | `sa_until_budget` |
| ga | 遺伝的アルゴリズム（下記） | `ga_plugboard` |

### GA の設計

| 項目 | 内容 |
|---|---|
| 個体 | plugboard（26 文字の対合、ペア数は 10 以下） |
| 初期集団 | 空の plugboard 1 個 ＋ 0〜10 ペアをランダムに繋いだ plugboard |
| 選択 | トーナメント選択（3 個体） |
| エリート保存 | 上位 2 個体をそのまま次世代へ |
| 交叉（確率 0.9） | ペア単位の一様交叉。両親に共通するペアは必ず受け継ぎ、残りは両親のペアから無作為な順に、文字が衝突しないものを足す。子のペア数は両親のペア数の間で無作為 |
| 突然変異 | SA と同じ 3 種類の手（ADD/SWAP・REMOVE・PARTNER-SWAP）。確率 0.5 で 1 手ずつ追加（幾何分布）。親と同じ子は必ず 1 手動かす |
| 適応度 | 現行 HC と同じく IC → bigram → trigram+quadgram に段階的に切り替える（GA 部分の予算を 3 等分。切り替え時に集団を再評価） |
| 終了処理 | 予算の 5% を残して世代交代を止め、残りで最良個体を trigram の貪欲 HC で磨く |
| 個体数 | 64 |

## 公平性のための条件

- **評価予算**: 「適応度評価の回数（1 回の復号＋採点）」でそろえた。各試行（ケース×シード）で
  まず current を実行し、**候補ごとに**実際に使った評価回数を記録して、hc・sa・ga にはその回数を
  候補ごとの上限として与えた。IC・bigram 段の評価も 1 回と数える。
- **乱数シード**: 全手法で同じ `run_seed`（1〜N）。候補ごとの乱数列は候補の通し番号と `run_seed` から作る。
- **評価関数**: 言語モデルは全手法で同じ（大規模 n-gram 表）。各手法が返すスコア、候補の順位付け、
  Phase B（リング再探索）、最終スコアは全手法で共通のコードを通る。
- **テストケース**: 固定シードで生成（セット A=1001、B=2002、調整用=3003）。平文は
  `corpora.py` の `ENGLISH_CORPUS`（大規模 n-gram 表の学習には使われていない組み込み英文）から切り出し、
  評価用（A・B）は先頭 2,000 字、GA の調整用は残り 961 字と、範囲を分けた。
  ローター順・初期位置・プラグボードは無作為、リング設定は selftest と同じ (0,0,0)。
- **Phase A は共有**: 乱数を使わないので、ケースごとに 1 回だけ実行して全手法に同じ候補を渡した。
- **モード**: `accuracy`（既定）。言語は `english`（selftest と同じ）。最大 10 ペア。
- **実時間**: 手法の実行順をケース・シードごとにずらし（current は予算の基準なので常に先頭）、
  同じマシンで逐次実行した。

計測は 2 段階で行った。

- **pipeline**: 既定の解読と同じ流れ（Phase A → C → B）で、第 1 候補を平文と比べる。
- **oracle**: 正解のローター順・初期位置だけを Phase C に渡し、最適化手法そのものを比べる。

## GA のパラメータ調整

調整には評価に使わない調整用セット（35〜120 字・2〜10 ペア・12 ケース、`--set tune`）を使い、
oracle だけで current と GA を比べた（6 シード、計 72 試行）。

1 項目ずつ既定構成から変えた。「勝-分-負」は同じ試行の current と比べた適応度の勝敗。

| GA の構成 | 完全復元 | 適応度/字 | 対 current 勝-分-負 | 評価回数/候補 |
|---|---|---|---|---|
| 既定（個体数 64・段階スコアあり・突然変異 0.5・トーナメント 3・エリート 2・交叉 0.9・磨き 5%） | **60/72** | **-5.6287** | 4-58-10 | 67,609 |
| 段階スコアなし（trigram のみ） | 56/72 | -5.7390 | 3-56-13 | 67,610 |
| 個体数 32 | 55/72 | -5.8241 | 3-53-16 | 67,609 |
| 個体数 128 | 56/72 | -5.7307 | 4-55-13 | 67,635 |
| 突然変異 0.3 | 55/72 | -5.7801 | 3-54-15 | 67,636 |
| （参考）current | 63/72 | -5.5282 | - | 70,825 |

試した中では既定構成が最良だったので、これを `GaParams::default()` とした。
段階スコアを外すと明確に悪化しており、現行 HC と同じく「IC/bigram で荒く当ててから trigram」が
GA でも効いている。調整の途中で作業が中断したため、突然変異 0.8・トーナメント 2/5・
磨き 0/2%・交叉 0.6・エリート 1/4 は**試していない**。
どの構成でも、調整用セットで current を上回るものは無かった。

## 結果

表の見方:

- **完全解読**: 第 1 候補の復号文が平文と完全一致した試行数（oracle では plugboard の完全復元と同じ）
- **文字一致率**: 第 1 候補の復号文と平文の、位置ごとの一致率の平均
- **適応度/字**: 第 1 候補の復号文の Phase C 適応度（trigram + 0.5×quadgram の対数確率和）を
  字数で割った値の平均。大きいほど良い（平文そのものの値を上回ることもある＝過学習）
- **対現行 勝-分-負**: 同じケース・同じシードの current と比べて、適応度が高い/同じ/低い試行数
- **評価回数/候補**: 候補 1 つあたりの適応度評価回数の平均（予算がそろっていることの確認）
- **時間**: 1 試行あたりの平均。Phase C は Rust 部分の実時間、合計は Phase B を含む（pipeline のみ）

## 考察

- **GA は現行より弱い。** oracle では、短文・多ペアで差がつくケース（A の 0〜2、B の 5・6 など）で
  GA の完全復元が現行を下回り、適応度の勝敗も 11-16-23（A）、11-12-27（B）と負け越した。
  長文・少ペア（A の 7〜9、B の 2・4）は全手法が満点で差が出ない。
- **GA の評価回数は予算より約 4.6% 少ない**（A の oracle で 76,298 対 79,973）。最後の HC 磨き用に
  残す 5% を、磨きが使い切らないため。GA にとって不利な条件だが、差（完全復元で 4〜6 件）を
  この 4.6% だけで説明できるかは確かめていない（未検証）。
- **実時間も GA が少し遅い。** 評価回数は同じかやや少ないのに、Phase C は oracle で約 +0.02 秒、
  pipeline で +0.7〜1.5 秒（約 8〜25%）長い。交叉・並べ替えなど評価以外の処理の分と考えられる（未検証）。
- **pipeline では Phase C の手法差が完全解読に出なかった。** 今回の 20 ケースでは、Phase A が
  正解を Phase C に渡す候補に入れたケースが 1 つもなかった。このため、どの手法でも完全解読は 0 で、
  解読率を左右しているのは Phase C ではなく Phase A（候補の取りこぼし）だった。
  README にある「50〜150 字×2〜10 ペアで 10/10」は、今回のセット A（平均 8.2 ペア）では再現しなかった。
  README の 10 ケースの中身（ペア数の分布・平文）は記録が無く、同じ条件かどうかは確かめられない。
- **SA 単独は現行を一貫しては上回らない。** 5 シードの oracle では、SA（SA＋HC 磨きの再スタート）が
  完全復元 23 対 21（A）・19 対 18（B）と上回ったため、採用の可否を見るために current と SA だけを
  15 シードで追加検証した（下表）。A では SA が +8 だったが、B と調整用セットでは −1 で、
  文字一致率も B で −2.6 pt だった。セットによって向きが変わる差なので、既定は変えなかった。

  | セット（oracle・15 シード） | current 完全解読 | sa 完全解読 | current 文字一致率 | sa 文字一致率 | current 適応度/字 | sa 適応度/字 | sa の対現行 勝-分-負 |
  |---|---|---|---|---|---|---|---|
  | A（150 試行） | 58 (39%) | 66 (44%) | 46.8% | 53.6% | -6.2477 | -6.0967 | 56-54-40 |
  | B（150 試行） | 56 (37%) | 55 (37%) | 47.1% | 44.5% | -5.9146 | -5.9045 | 52-56-42 |
  | 調整用（180 試行） | 159 (88%) | 158 (88%) | 89.7% | 88.5% | -5.5076 | -5.5322 | 13-153-14 |
- **HC 単独は現行より弱い**（完全復元 17 対 21、11 対 18）。現行の SA 磨き上げには効果がある。

## 制約・やらなかったこと

- **シード数**: pipeline は時間の制約（全体で約 60 分）から 3 シードに減らした（依頼の目安は 5）。
  oracle は 5 シード。ベンチマークの実行時間は pipeline A 24.5 分・B 14.8 分・oracle 1.0 分の計 40.3 分
  （GA の調整 約 10 分と、SA の 15 シード追加検証 2.3 分は別）。
- **GA の調整は途中まで**: 5 構成を試したところで中断し、残りの構成（上記）は試していない。
  より良いパラメータが存在する可能性は残る。
- **リング設定は (0,0,0) 固定**: selftest と同じ。リングが 0 以外のケースは比べていない。
- **言語は英語のみ**（`--lang english`）。ローマ字・`auto` は比べていない。
- **実時間は参考値**: 同じマシンで逐次実行したが、計測中の負荷は管理していない。予備計測では同じ
  処理の Phase C が 5.2〜8.2 秒とばらついた。
- **Web 版（`web/`、`wasm.rs`）には GA を入れていない**。GA は CLI の `--optimizer ga` と
  Python の `attack_plugboard(optimizer='ga')` からだけ使える。

## 再現手順

グローバルの Python を汚さないよう、仮想環境に Rust コアを入れて実行する
（Windows / Git Bash の例。`uv` と Rust ツールチェーンが入っている前提）。

```bash
cd enigma-decoder
VENV="$TEMP/enigma-bench-venv"           # リポジトリの外に作る
uv venv "$VENV"
uv pip install --python "$VENV/Scripts/python.exe" maturin
cd enigma_decoder
PYO3_USE_ABI3_FORWARD_COMPATIBILITY=1 \
  "$VENV/Scripts/maturin" build --release --out "$TEMP/enigma-bench-wheels"
cd ..

# pipeline + oracle（3 シード）。10 分以内に収まるようケース範囲で分けて実行し、最後に合算
```

適応度・完全解読・評価回数は乱数シードで決まるので、同じビルドなら同じ値が出る。
実時間はマシンと負荷で変わる。

GA を実際の解読で使うときは `--optimizer ga` を付ける（既定は従来どおり `staged`）。

```bash
python decrypt_plugboard.py --optimizer ga --selftest
python decrypt_plugboard.py --optimizer ga --lang english <暗号文>
```

CLI の GA は、候補あたり `(1 + n_restarts) × 7,000 + sa_steps` 回の評価を予算にする
（`ga_budget_per_candidate`）。7,000 は段階スコア HC 1 回あたりの実測（`n_restarts=4` で
現行は候補あたり約 72,500 回、`n_restarts=6` で約 86,000 回）からの見積もり。
